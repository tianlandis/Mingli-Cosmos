# ADR-009: 支付接入与回调幂等

- **状态**: `Proposed`
- **日期**: 2026-09-28
- **决策者**: 田哥
- **类别**: 🧱 骨架（计费闭环）
- **关联**: `../arch/ARCHITECTURE-REVIEW.md` §3、`src/server/modules-public/billing/`、`src/server/db/schema.ts`（`orders.payMethod`）

---

## 背景（Context）

订单流程已具备（下单 → 模拟支付 → 订阅），但 `payMethod='mock'` 是**空壳** ——
没有真实支付网关，无法真实收款。

接入真实支付（微信 / 支付宝）时，最大的风险是**回调重复 / 乱序导致重复发货**
（重复开通订阅、重复加额度）。这是计费闭环能否成立的**关键承重柱**。

## 驱动因素（Decision Drivers）

- 商业化的前提是**能真实收款**。
- 支付回调**必定会重复 / 乱序**（这是分布式支付的常态，非异常）→ 幂等是**强制项**。
- 发货必须**可审计**，与 ADR-004 的台账一致。

## 决策（Decision）

1. **首选微信支付 + 支付宝**（面向境内用户）；先做**一个**跑通闭环，再做第二个。
2. **支付 = 状态机**：`created → pending → paid → fulfilled / closed / refunded`，
   每次流转落 `orders` + 审计。
3. **回调幂等（强制）**：
   - 以**支付方交易号 + 商户订单号**做唯一约束；
   - 回调处理**必须幂等**：已处理过的回调直接返回成功（不重复发货）；
   - 回调中**先验签 → 再校验金额 → 后发货**，顺序不可颠倒。
4. **发货 = 写 ledger**（ADR-004）：加额度 / 开订阅都走可审计的台账。
5. **对账**：提供"支付方流水 vs 本站订单"的每日对账能力（后台报表）。
6. **退款 / 争议**：先做后台"退款回收"（已具备雏形），后续再自动化。

## 后果（Consequences）

**正向 (+)**
- 能真实收款；重复回调不重复发货；对账可查。

**负向 (−)**
- 引入外部依赖（证书 / 商户密钥管理）与运维（回调域名必须公网可达 + HTTPS）。

**中性 / 风险**
- 微信支付需要**备案域名 + HTTPS**（当前用 IP 直连）→ 上真实支付前必须先解决域名与证书。

## 复审触发条件

- 引入订阅自动续费 → 需签约代扣能力；
- 增加支付渠道（如 Stripe / PayPal）→ 抽象支付适配层。
