# ADR-002: SQLite → PostgreSQL 的迁移触发条件

- **状态**: `Proposed`
- **日期**: 2026-09-28
- **决策者**: 田哥
- **类别**: 🧱 骨架（存储形态）
- **关联**: `../arch/ARCHITECTURE-REVIEW.md` §4.1、`src/server/db/index.ts`

---

## 背景（Context）

当前存储为 **SQLite（better-sqlite3，WAL）**，单文件 `/app/data/mingli.db`，跑在挂卷上。
SQLite 的优点（零运维、单文件、事务简单）与当前阶段高度匹配；但它是**单写者**，
无法多实例水平扩展，且与"多副本 / 读写分离 / 异地容灾"等规模化需求冲突。

盲目迁移 PostgreSQL 会立刻引入运维面，属于"为不需要的规模买单"。
但迁移成本随数据量线性上升，因此必须**提前定义触发条件**，到点即迁，避免被动。

## 驱动因素（Decision Drivers）

- 现在：单机、单实例、写并发低 → SQLite 足够。
- 未来：多实例、写并发升高、单表体量增长 → SQLite 成瓶颈。
- SQLite 是**同步驱动**，重查询会阻塞 Node 事件循环，拖慢全进程。

## 决策（Decision）

**继续使用 SQLite**，但设定明确的**迁移触发条件**（命中任一即启动 PostgreSQL 迁移）：

| # | 触发条件 | 判据 |
|:--:|---|---|
| T1 | 并发写冲突 | 出现 `SQLITE_BUSY` 频率上升，重试率 > 0.5% |
| T2 | 单表规模 | 任一业务表行数 > 1000 万（优先观察 `sessions` / `analytics_events`） |
| T3 | 需要多实例 | 上线第 2 个应用副本 / 需要读写分离 |
| T4 | 可用性要求 | 业务要求 RPO < 5min 或 RTO < 5min（SQLite 单文件难达标） |
| T5 | 运维诉求 | 需要在线 DDL / 行级锁 / 成熟备份工具链 |

**迁移预案**（届时另开 ADR，此处先定方向）：

1. 引入 Drizzle 的 PG dialect，SQL 尽量保持方言无关；
2. **版本化迁移链先行**（见 ADR-008），确保两库结构一致；
3. 双写灰度 → 数据校验 → 切读 → 切写 → 下线 SQLite。

## 后果（Consequences）

**正向 (+)**
- 零运维、快、够用；迁移有明确"起跑线"，不是拍脑袋。

**负向 (−)**
- 单写天花板保留至迁移完成；同步驱动需避免大表全扫。

**中性 / 风险**
- T2 若靠 `sessions` 撑爆，说明没做 TTL（见 ADR-008）—— 应优先补保留策略而非直接换库。

## 复审触发条件

- 上述任一 T1~T5 命中；
- 或业务形态变化（如需强一致多写、跨地域多活）。
