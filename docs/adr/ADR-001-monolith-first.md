# ADR-001: 单体优先 —— 为什么现在不拆微服务

- **状态**: `Proposed`
- **日期**: 2026-09-28
- **决策者**: 田哥
- **类别**: 🧱 骨架（结构形态）
- **关联**: `../arch/ARCHITECTURE-REVIEW.md` §6、§2

---

## 背景（Context）

Mingli-Cosmos 目前是一个**模块化单体（Modular Monolith）**：单个 Hono 进程同时承载
C 端 API（`/api/v1/app/*`）、管理端 API（`/api/v1/admin/*`）、AI 编排（`/api/chat`、`/api/report`）
与命理引擎，数据落在一个 SQLite 库上。部署在单台 2 核 961MB 的 VPS。

未来 6~12 个月的主要目标是**验证商业模型**（Freemium 变现、留存、口碑），而不是承担超大流量。

评审已识别出若干"缝隙未预留"的问题（见 `ARCHITECTURE-REVIEW.md` §2），
但**没有任何证据表明当前规模需要进程级拆分**。真正的问题是"承重柱没立起来"，
而不是"单体这一形态选错了"。

## 驱动因素（Decision Drivers）

1. **团队规模小**（个人 / 小团队），运维人力有限。
2. **部署资源紧张**（单机 961MB，多进程会放大内存与部署成本）。
3. **业务以 CRUD + LLM 调用为主**，没有复杂到需要独立扩缩容的域。
4. **可逆性优先**：现在拆 = 不可逆的复杂度负债；边界焊牢后再拆 = 低风险重构。
5. 代码库**边界已较清晰**（engine 封版、模块自动扫描、双鉴权隔离），具备"随时可拆"的基础。

## 备选方案（Options）

### Option A：加固模块化单体 + 预留拆分缝 ⭐
保持单进程单库，把三个未来要拆的模块（**AI 编排 / 计算权威 Chart / 计费**）的边界"焊牢"，
使未来拆分退化为"把目录搬到独立进程 + 换传输"，而非重写。
- **代价**：单写 SQLite 的扩展天花板仍在；需接受"规模到了再拆"的一次性成本。

### Option B：现在就拆服务（引擎 / AI 网关 / 业务 / 管理 4 进程）+ 迁 PostgreSQL
- **代价**：运维复杂度、分布式一致性、部署成本陡增；961MB 单机上不现实；团队维护面放大。

### Option C：事件驱动 + CQRS
- **代价**：对"CRUD + LLM 调用"为主的业务属于**过度设计**（架构宇航员）。

## 决策（Decision）

**采用 Option A。** 明确三条"拆分缝"，并在演进中保持其边界：

1. **AI 编排** 收敛为独立模块边界（未来 → LLM 网关服务，见 ADR-003）；
2. **计算权威** 收敛为单一 Chart 模块（见 ADR-005）；
3. **计费** 收敛为独立上下文（见 ADR-004 / ADR-009）。

在此之前**不引入新进程、不引入消息队列**。任何为"将来可能拆分"而增加的抽象，
必须能在当前单体里被单测覆盖，否则拒绝引入。

## 后果（Consequences）

**正向 (+)**
- 交付速度最快、运维面最小、可逆性最高。
- 拆分的"缝"提前定义，未来拆分是**重构而非重写**。

**负向 (−)**
- 单写 SQLite 的扩展天花板保留（由 ADR-002 的换库触发条件兜底）。
- 管理端重操作与 C 端争抢 CPU（见 `ARCHITECTURE-REVIEW.md` §R-3），需靠监控分维度观测延迟。

**中性 / 风险**
- 若长期不拆，模块边界可能被侵蚀 → 以"模块禁止直接读其它模块的表 / 仓库"作为纪律约束。

## 复审触发条件

出现**任一**即重评本决策：

- 需要多实例水平扩展（受 SQLite 单写阻塞）；
- admin 跑批明显拖慢 C 端，且无法通过调度错峰解决；
- 单进程 CPU / 内存成为常态瓶颈；
- 团队扩张到多个可独立负责的业务小组。
