# ADR-010: API 版本与弃用策略（含 `/api/admin` 退场）

- **状态**: `Proposed`
- **日期**: 2026-09-28
- **决策者**: 田哥
- **类别**: 🔧 完善（演进纪律）
- **关联**: `../arch/ARCHITECTURE-REVIEW.md` §R-4、`src/server/core/app.ts`

---

## 背景（Context）

`src/server/core/app.ts` 保留了 `/api/admin/*` 兼容层 + `Deprecation` 头，标注"30 天过渡"。
双份维护成本随接口增多而放大；API 演进若无统一纪律，客户端将长期锁死在旧契约上。

此外，支付回调（ADR-009）、开放 API（Phase 8）等对外接口即将出现，**现在正是立规矩的时机**。

## 驱动因素（Decision Drivers）

- 避免"永久双份维护"（兼容层一旦续期就变成技术债）。
- 对外接口需要明确的**版本与弃用契约**，否则集成方无法安全升级。
- 契约先行（仓库已有 `docs/contracts/` 传统）应延伸到 HTTP API。

## 决策（Decision）

1. **版本策略**：对外 API 一律带版本前缀（现有 `/api/v1/*` 保持）；
   **破坏性变更升版本**，不原地修改。
2. **弃用流程**：`Deprecation` 头 + `Sunset` 日期 → 公告期（≥ 30 天）→ 关停；
   关停前**统计调用量**，确认无流量后再删。
3. **`/api/admin` 兼容层**：过渡期到点即**删除**（不续期）；删除前确认无调用方。
4. **契约优先**：接口变更先更新 `docs/contracts/`，再改实现。

## 后果（Consequences）

**正向 (+)**
- 避免双份永久维护；客户端升级有明确时间盒。

**负向 (−)**
- 短期需维护两版（受控）。

**中性 / 风险**
- 外部集成方未及时升级 → 用**调用量统计 + 公告**兜底，避免"盲删"。

## 复审触发条件

- 开放 API（Phase 8）对外 → 需补充鉴权 / 配额 / SLA 契约；
- 兼容层调用量长期不为零 → 需排查残留调用方而非无限期保留。
