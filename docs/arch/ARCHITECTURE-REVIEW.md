## 0. 结论先行（TL;DR）

| 判断 | 结论 |
|---|---|
| **架构模式** | 当前是**边界清晰的模块化单体（Modular Monolith）**，与团队规模/阶段**匹配良好** |
| **是否需要重写** | **不需要**。方向正确，问题是"缝隙未预留 + 商业化闭环缺失"，不是模式选错 |
| **本期建议路线** | **加固模块化单体 + 预留拆分缝**（Option A）；随规模按缝拆分，**现在不上微服务** |
| **架构动作优先级** | 商业化闭环 > 可运维性/可观测性 > 数据层健壮性 > PII 合规 > AI 成本治理 |
| **Top 5 风险** | ① 计费闭环缺失（无法真实收款、额度未强制）② SQLite 单写 + 无备份策略 ③ 计算 SSOT 违背（客户端算、服务端信任）④ LLM 无缓存/无成本核算/无限流门禁 ⑤ 可观测性停留日志级、无 SLO |

> **一句话**：这不是一个"架构要推倒"的项目，是一个"架构骨架对了、缺几根承重柱"的项目。接下来 6 个月的重点是**把商业闭环和运维底座补上**，而不是拆服务。

## 2. 分层与边界评估

### ✅ 做得好的（保留，不要动）

| # | 设计 | 价值 |
|:--:|---|---|
| 1 | **引擎封版 + 契约消费**（`engine/index.ts` 单一出口，CODEBUDDY.md 红线） | 算法与外围解耦，引擎可独立复用/测试 |
| 2 | **模块自动扫描路由器**（`core/router.ts` `createModuleRouter`） | 加后台模块 = 放一个目录，零注册代码，可插拔 |
| 3 | **知识资产单一来源**（`knowledge_assets` 35 项 → 同时驱动引擎与 Prompt） | 规则不写死在代码/Prompt 里，多端算法一致 |
| 4 | **双鉴权隔离**（`admin_sessions`/`user_sessions` + 两套 JWT 密钥） | 后台与 C 端权限边界干净，互不越权 |
| 5 | **三轨配置 + 热更新**（api_keys→app_configs→.env，60s 缓存 + `reloadConfig`） | 换 Key/换模型免重启 |
| 6 | **反幻觉双保险**（System Prompt 约束 + `anti-hallucination` / `guardrail` 后校验） | 约束 LLM 不脱离规则 JSON 编造 |
| 7 | **审计日志**（`audit_logs` + `audit.ts` 中间件） | 后台变更可追溯 |

### ⚠️ 需要正视的边界问题（带证据）

#### 🔴 R-1 计算 SSOT 违背：算在客户端，服务端"盲信"

- **证据**：`src/hooks/useBazi.ts` 在浏览器里调 `calculateBazi` + `generateAnnotation`；`src/server/api/report.ts:13-18` 与 `src/server/api/chat.ts:106-120` 只做**存在性校验**后**直接使用**客户端传来的 `chart`/`annotation`。
- **后果**：① "AI 必须基于规则引擎 JSON、禁止编造"这条红线，**事实源其实由客户端掌握** —— 构造一个伪造的 `annotation` 就能让 AI 基于假数据输出；② admin 改 `knowledge_assets` 后服务端引擎会 reload，但**客户端 bundle 里的引擎是构建期固化的**，用户看到的批注与 LLM 工具重算的结果**可能不一致**（漂移）。
- **这是本次评审最重要的发现**：它同时是**完整性风险**和**一致性风险**。
- **建议**：确立唯一权威——要么服务端权威（新增 `POST /api/v1/app/chart` 由服务端算并落 `sessions`，`report/chat` 只收 `sessionId`），要么明确客户端权威并**在服务端重算校验哈希**（`chartHash` 比对）。详见 ADR-005。

#### 🟡 R-2 "引擎封版不可变" 与运行时 reload 的语义矛盾

- **证据**：文档称引擎"封版、不修改"，但 `services/KnowledgeProvider.ts` 在运行时 `reloadBranchRelations` / `reloadShenShaRules` / `reloadPatternRulesData` 等**注入并替换引擎内部数据表**。
- **判断**：这是**数据注入**（可接受），但文档没区分"逻辑封版"与"数据可变"，容易被后来者误解为可以随便改引擎逻辑。
- **建议**：文档显式定义为「**引擎逻辑封版 / 数据表运行时可热加载**」两条独立规则。

#### 🟡 R-3 管理端与 C 端同进程，无资源隔离

- **证据**：`core/app.ts` 单 Hono 应用同时挂载 `/api/v1/admin/*` 与 `/api/v1/app/*`。
- **后果**：后台重操作（如知识资产全量导出、批量维护）会与 C 端抢 CPU/内存。当前 2 核 961MB，**后台跑批时 C 端会有可感抖动**。
- **判断**：现阶段可接受（模块化单体的固有代价），但需在监控里**把 admin 与 app 的延迟分开看**，作为拆分的触发信号。

#### 🟢 R-4 遗留双栈路由（/api/admin 兼容层）

- **证据**：`core/app.ts:63-69` 保留了 `/api/admin/*` 兼容 + deprecation 头，"30 天过渡"。
- **建议**：到点就该删，否则长期双份维护。

| 上下文 | 承载物（现有） | 边界清晰度 | 备注 |
|---|---|---|:--:|
| **命理计算** | `src/engine/*` | 🟢 极高 | 纯函数、无语境、封版 |

| **AI 编排** | `api/chat.ts`、`agents/`、`workflows/`、`prompts/`、`lib/llm.ts` | 🟡 中 | 与配置、工具、配额交织，需收敛为"LLM 网关" |
| **身份与访问** | `users`/`user_sessions`/`admin_sessions` | 🟢 高 | 双轨已隔离 |

## 4. 扩展性评估（四维）

### 4.1 数据维度

| 项 | 现状 | 天花板 / 风险 |
|---|---|---|
| 存储 | SQLite 单文件 + WAL（`db/index.ts:31-33`） | **单写者**：无法多实例水平扩展；写并发≈单进程 |
| 读扩展 | 无读写分离、无副本 | 读压力全压主库 |
| 表膨胀 | `sessions`（整份 chart+annotation JSON）、`analytics_events`、`audit_logs` **无 TTL/清理** | 长期无界增长，查询退化 |
| 备份 | **无备份脚本、无恢复演练、无 PITR** | 🔴 生产库仅靠一个卷，误删/损坏=数据全丢 |
| 迁移 | `migrate.ts` 幂等建表（`IF NOT EXISTS`），**无版本化迁移链** | 改列/改约束时无安全路径 |
| ORM | Drizzle + better-sqlite3（**同步 API**） | 同步驱动会阻塞事件循环，重查询拖慢全进程 |

**触发换库的信号**（写进 ADR-002）：并发写冲突出现 / 单表 > 千万行 / 需要多实例 / 需要读写分离 —— 任一成立即迁 PostgreSQL。

### 4.2 计算维度

- 引擎**无状态纯函数** → 天生可水平扩展（优点）。
- 但**计算在客户端**：服务端只有"重算校验"的需求（当前未做），所以服务端计算负载其实很低。
- 批注流水线（`annotation/engine.ts` 13 步串行）在客户端执行 → 复杂盘面会**阻塞浏览器主线程**；大报告走服务端 `workflows` 是**串行两步 LLM**（SOP-1→SOP-2），延迟叠加。
- **缺口**：无计算并发上限、无排队、无超时熔断（`llmTimeoutMs` 只覆盖 LLM，不覆盖流水线整体）。

### 4.3 AI 维度（**当前最大的成本/弹性敞口**）

| 能力 | 现状 | 缺口 |
|---|---|---|
| 响应缓存 | ❌ 无 | 常见问题重复付费（风险文档已列，未实现） |
| 限流 | 仅登录限流（已修）；**AI 接口无限流** | 单用户可无限刷 LLM，成本失控 |
| 配额门禁 | 有 `consumeQuota`，但 `quota_enforce_chat` **默认关** | 商业模型未生效 |
| 幂等 | `consumeQuota` 无幂等键 | 重试/双击可能重复扣额度 |
| 成本核算 | ❌ 无 token 计量、无账单 | 无法回答"这个用户花了多少钱" |
| 多供应商 | 只有**全局唯一** `isDefault=1` | 无故障转移；一次超时即用户可见失败 |
| 分级模型 | ❌ 无 | 文档设想"常见走 DeepSeek、深度走 Claude"未落地 |
| 降级 | 有 `Try<T>` + 部分回退 | 无 circuit breaker / 半开重试策略 |

### 4.4 部署维度

- **单容器单端口**，镜像构建**强依赖 swap**（961MB 内存，见部署实录）。
- 无灰度/金丝雀，回滚 = `git reset + rebuild`（分钟级，非秒级）。
- 健康检查**只有进程级**（`/api/health` 不探测 DB/LLM 上游）。
- 静态资源：SPA 设 `no-store`（`app.ts:123-124`）→ **放弃浏览器缓存**，首屏每次都拉 HTML（可接受，但应有 hash 资源长缓存策略）。
- **无 CDN、无反代配置入库**（用户自建，仓库里 `nginx.conf` 与线上不一定一致）。

## 6. 目标架构演进方案（3 选 1 + 权衡）

### Option A · 加固模块化单体 + 预留拆分缝 ⭐ 推荐

**动作**：保持单进程单库，把模块边界"焊牢"，同时把 AI 编排收敛成**可独立出的"LLM 网关"模块**、把计算权威收敛到**单个 Chart 服务模块**。
**代价**：单写 SQLite 的扩展天花板仍在；需接受"规模到了再拆"的一次性重构成本。

### Option B · 服务拆分（引擎服务 / AI 网关 / 业务服务 / 管理服务）

**动作**：拆 3~4 个进程，迁 PostgreSQL，独立扩缩容。
**代价**：运维复杂度、分布式一致性、部署成本陡增；**当前 961MB 单机上拆服务不现实**；团队维护面变大。

### Option C · 事件驱动 + CQRS

**动作**：写模型/读模型分离，事件总线驱动看板与额度。
**代价**：对"CRUD + LLM 调用"为主的业务**过度设计**（架构宇航员）。

### 权衡矩阵

| 维度 | A 加固单体 | B 服务拆分 | C 事件驱动 |
|---|:--:|:--:|:--:|
| 与当前阶段匹配 | ✅ 高 | ❌ 低 | ❌ 低 |
| 交付速度 | ✅ 快 | 🟡 慢 | ❌ 最慢 |
| 可维护性 | ✅ 好（边界已清晰） | 🟡 依赖团队 | ❌ 需成熟度 |
| 扩展天花板 | 🟡 中（单写） | ✅ 高 | ✅ 最高 |
| 运维成本 | ✅ 低 | ❌ 高 | ❌ 最高 |
| 可逆性 | ✅ 高 | 🟡 中 | ❌ 低 |

> **决策**：选 **A**。原则是「**可逆优先**」——现在就拆服务是**不可逆的复杂度负债**；而当 AI 网关、Chart 服务、计费三个模块边界焊牢后，**未来拆分是低风险的重构**，不是重写。

## 7. 长期发展规划（分阶段）

```
P5 商业化闭环         P6 AI 深化              P7 规模化               P8 生态
(1~2 月)             (2~4 月)               (4~8 月)               (8 月+)
─────────────────▶   ─────────────────▶    ─────────────────▶    ─────────────────▶
真实支付 + 额度门禁    LLM 网关 + RAG 知识库   服务拆分 + PG 迁移      开放 API + 小程序
+ 合规底座             + 多 Agent 完整实现     + 可观测性 + DR        + 社区 + 多端
```

### Phase 5 · 商业化闭环（先补承重柱）

| 目标 | 关键交付 | 架构动作 | 退出标准 |
|---|---|---|---|
| 能真实收钱 | 微信/支付宝接入、回调**幂等**、对账报表 | 计费上下文补全（ADR-009） | 真实支付链路冒烟通过 |
| 额度真实生效 | `quota_enforce_chat` 转正、订阅权益生效、超额引导 | 配额**幂等**消费（ADR-004） | 免费/付费行为差异可验 |
| 合规底座 | 隐私政策 + 用户协议 + 数据导出/删除 | PII 治理（ADR-006） | 合规清单全勾选 |
| 计算权威 | 服务端 Chart 端点 或 重算校验 | SSOT 收敛（ADR-005） | 伪造 chart 无法影响 AI 输出 |
| 运维底座 | 备份脚本 + 恢复演练 + 版本化迁移 | 数据健壮性（ADR-008） | 备份可恢复、迁移可回滚 |

### Phase 6 · AI 深化

| 目标 | 关键交付 | 架构动作 |
|---|---|---|
| 成本可控 | LLM 网关：缓存 + 成本核算 + 限流 + 降级 | ADR-003 |
| 分级路由 | 免费用户→便宜模型，付费→强模型 | LLM 网关内策略 |
| 知识增强 | RAG（典籍库）+ 命例库 | 新增检索上下文 |
| 多 Agent 完整化 | Router + 专题 Agent 全量落地（现为骨架） | `agents/` 扩充 |

### Phase 7 · 规模化

| 目标 | 关键交付 |
|---|---|
| 脱离单写 | PostgreSQL 迁移（触发条件见 ADR-002） |
| 独立扩缩 | 拆出 AI 网关与 Chart 服务 |
| 可观测 | 指标/日志/追踪三件套 + SLO 看板（ADR-007） |
| 容灾 | 多副本 + 异地备份 + 演练 |

### Phase 8 · 生态

开放 API、小程序、合婚/择吉、社区、（可选）独立 App。
